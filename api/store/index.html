    Store API¶

    LangGraph long-term memory stores for CockroachDB.

    CockroachDBStore¶

    Synchronous store.

    langchain_cockroachdb.store.store.CockroachDBStore ¶

    Bases: BaseStore, BaseCockroachDBStore, PsycopgOps

    LangGraph store that keeps long-term memory in CockroachDB.

    Items live in one table keyed by namespace and key. Namespaces are stored as their labels joined with ".". For production, pass a psycopg_pool.ConnectionPool or use from_conn_string with pool_config: a pool replaces broken connections and runs batches concurrently, while a single connection runs one batch at a time.

    A batch runs its reads first, then all its puts and deletes in one transaction. Its gets, its searches and its listings take one round trip each. On a store with a vector index, semantic searches under a namespace add one before the searches, to find their namespaces, and one after them when a search must run again exactly. A flat store adds neither. The long-term memory guide explains why.

    With history, a batch that overwrites or deletes a memory first copies the version it ends into a history table, in its transaction. delete then keeps the memory in history; purge removes a memory with its history, and history lists the old versions.

    Example 
    from langchain_cockroachdb import CockroachDBStore

with CockroachDBStore.from_conn_string(
    "cockroachdb://root@localhost:26257/defaultdb?sslmode=disable"
) as store:
    store.setup()
    store.put(("users", "123"), "prefs", {"theme": "dark"})
    item = store.get(("users", "123"), "prefs")

    confirm(namespace, key, *, ttl=NOT_PROVIDED) ¶

    Mark a live memory as confirmed, renewing its expiry and counting confirmations.

    This counts the confirmation and renews the expiry. That way expiry can follow how often a fact is confirmed, not how often it is read. Confirming does not change the version or updated_at, so it never invalidates a pending find_conflicts. Confirmations belong to the memory's value: a write that changes it starts them again from none.

    Each call picks a confirmation id before its first attempt and stores it on the memory, so a retry after a commit whose result was lost counts nothing again, unless another confirmation of the same memory lands in between, in which case the retry counts again. The memory's write id stays as it is, so a write retried after its own lost commit still finds it.

    delete_if(namespace, key, *, expected) ¶

    Delete a memory only if it is still the one the caller read, in one transaction.

    delete_if deletes only if the live memory under key still has the version and updated_at of expected, as put_if checks them. On a match it deletes as delete does: on a store with history the memory is kept in history as deleted, and its vectors go. With expected=None it applies only while no live memory has the key, so it deletes nothing live.

    applied=True means the memory matched expected and this call deleted it, or, after an earlier attempt of the call that may have committed, that the memory is gone and was this call's to delete: it matched expected when that attempt checked it. On a mismatch it deletes nothing and returns applied=False with current, the live memory as the same transaction read it, or None if there is none, as when another writer deleted it or it expired since. A conflict is returned, not raised.

    If an attempt sends its COMMIT and the result is lost, as when the connection drops while the COMMIT's answer travels, that attempt may have deleted the memory, so a retry that finds it gone reports it applied. On a store with history the retry also finds its own history row, which proves the earlier attempt deleted the memory, and the result has already_applied. A store without history keeps no row that proves which attempt deleted it, so already_applied stays False. Serialization failures and deadlocks (40001, 40P01) roll attempts back, so after only those a memory gone since is a conflict: another writer removed it. Once an attempt may have committed, the retries after it stay lenient, whatever error ends them next. If another writer put the key again before the retry, the retry reports a conflict with that memory.

    disable_ttl() ¶

    Turn off CockroachDB row-level TTL on the store's tables.

    Expired items are still left out of reads while omit_expired is on. Safe to run from several processes at once. On CockroachDB v25.4 a TTL change fails while another schema change runs on the same table; that error is retried with the budget that schema_change_policy gives it, up to ten minutes by default, even if the policy's retry_on would refuse it. max_attempts=1 turns this off.

    drop_vector_index() ¶

    Drop the store's vector index, if it exists.

    find_conflicts(namespace, key, value, *, slot=None, threshold=None, limit=10, filter=None, index=None, ttl=NOT_PROVIDED, provenance=None, valid_at=None) ¶

    Find the memories a new one may conflict with, without writing anything.

    Candidates are live memories in namespace itself, not in its descendants, for one of three reasons, strongest first:

    • "key": the memory under key, whatever filter says.
    • "slot": with slot, the memories whose value holds the same value in that field, compared as JSON.
    • "similar": on a store with an index, the memories whose vectors score at or above threshold against the new memory's, with the store's score function: 1 minus the distance on a cosine store, the negated distance on an l2 or inner_product store. The new memory is embedded as a document (embed_documents), while search embeds its query (embed_query), so with a model that embeds the two differently the scores differ from search's.

    Key and slot matches carry their best score when they have vectors, and similar ones always do. Candidates come strongest reason first, then best score, then key. Expired memories are never candidates, and no read pushes back an expiry.

    The index fields of value are embedded once, and the embedding is kept for the write. Then two round trips read the candidates: first the database's clock, the key and slot matches and the namespace's vector count, then the similar memories and the scores. A namespace with at most reconcile_scan_limit vectors has all of them ranked. A larger one takes its similar candidates from a window of the C-SPANN index. When that window holds nothing below threshold and gave fewer than limit candidates, matches may lie beyond it, and one more round trip ranks every vector of the namespace.

    history(namespace, key=None, *, limit=20, offset=0) ¶

    The old versions of a memory, or of every memory in a namespace, newest first.

    A store with history keeps every version that a write ends: one a put overwrites (reason "overwritten"), one a delete ends ("deleted"), and one that reconcile or resolve supersedes ("superseded", with superseded_by naming the memory that replaced it). A new memory that reconcile or resolve records as already superseded by a newer fact is kept there too, as "superseded". The live value is not one of them; get() returns it.

    Without a key, it lists the old versions of every memory in exactly namespace, not its descendants, as get() reads a namespace. That is how to find the old versions of memories that reconcile saved under keys the store generated. Each version carries its own key and superseded_by, so versions can be grouped by a field of their value, or followed to the memory that replaced them. Each call reads the namespace's whole history to sort it, which suits per-user namespaces. For a very large history, page with limit and offset.

    put_if(namespace, key, value, *, expected, index=None, ttl=NOT_PROVIDED, provenance=None, valid_at=None) ¶

    Write a memory only if it is still the one the caller read, in one transaction.

    Two threads that read the same memory with record() and both write it back with put would lose one update without a word. put_if writes only if the live memory under key still has the version and updated_at of expected, the check resolve makes: a put moves the version, and a 0.5.x store, which does not, still moves updated_at. With expected=None it writes only if no live memory has the key, so a memory is created once. An expired memory counts as absent.

    On a match it writes as put does, in the transaction that checked: the write id goes on the row, the version it replaces is kept in history on a store with history, ending at valid_at when given or else at the write, and the memory's vectors are replaced. The result has applied set and the version written.

    On a mismatch it writes nothing and returns applied=False with current, the live memory as the same transaction read it, or None if there is none. A conflict is an expected outcome here, so it is returned, not raised: merge and call put_if again with current, keep the stored memory, or ask the user.

    The index fields of value are embedded once, before the first attempt. If an attempt commits and its result is lost, as when the connection drops while the COMMIT's answer travels, the retry finds the write id on the row and returns applied=True with already_applied. If another writer replaced the memory before the retry, a 0.5.x store included, the retry reports a conflict with that writer's memory, which is the current state.

    reconcile(namespace, key, value, *, policy, slot=None, threshold=None, limit=10, filter=None, index=None, ttl=NOT_PROVIDED, provenance=None, valid_at=None) ¶

    Write a memory and settle the memories it may conflict with, in one transaction.

    The candidates are the ones find_conflicts finds: the live memory under key, the memories in the same slot and, on a store with an index, those that score at or above threshold. They are read in the transaction, policy decides what to do with the new memory and with each candidate, and the decision is applied before the transaction commits. Serializable isolation covers all of it: if another writer changes what the policy saw, one of the two transactions retries, and its policy sees the other's write. Two agents that reconcile contradicting memories for one user cannot both win.

    policy runs inside the transaction, and runs again on every retry, so it must be a plain function, fast and deterministic: an async function is refused before any I/O. A slow policy holds the transaction open and can run past the attempt timeout. An LLM judge, or a person, belongs in find_conflicts and resolve, which hold no transaction while the decision is made. A policy must not call the store either: the store holds its connection while the policy runs, so such a call raises RuntimeError at once. A policy that raises rolls the transaction back, and its exception propagates unchanged, without a retry. So does the ValueError for an invalid decision.

    The decision writes the new memory, as put does, with its provenance and valid time; skips it, as when it repeats a memory the decision confirms; or records it as superseded by a candidate whose fact is newer. A store with history records such a late fact straight into history; a store without history skips it. Each candidate is kept, superseded, deleted or confirmed. On a store with history, every version the decision ends is kept in history: the memory the new one overwrites and each candidate it supersedes end at the valid_at given, or at the write without one, and deleted ones end at the write. Without history, superseding and deleting remove the memory. Confirming sets confirmed_at, counts the confirmation and renews the memory's expiry from its own TTL. It changes neither the version nor updated_at.

    The index fields of value are embedded once, before the first attempt. Each attempt reads the candidates in two round trips, as find_conflicts does, or three when the index's window may have left matches out. Then the policy runs, and the writes and the COMMIT go out together.

    If an attempt commits and its result is lost, as when the connection drops while the COMMIT's answer travels, the retry finds the rows that carry its write id and writes nothing. It returns the result rebuilt from those rows, with already_applied set. That result lists only what the rows prove: kept is empty, and on a store without history so are superseded and deleted. A confirmation of the new memory in between leaves the write id on it. If another writer replaced the new memory before the retry, the history row of the version it overwrote, or of a memory it superseded, still proves the write: the result says it was written, with no version.

    resolve(conflicts, decision) ¶

    Apply a decision about what find_conflicts found, in one transaction.

    This is the second step of the two-step flow: find_conflicts reads the candidates, an LLM or a person decides while no transaction is open, and resolve applies the decision as reconcile applies a policy's. It writes the new memory that find_conflicts planned, with its provenance, valid time and write id, and the vectors it embedded then, so nothing is embedded again. For the same reason it refuses a proposal edited after find_conflicts, rather than drop the edit: to change the memory, call find_conflicts again with the edited one.

    In the same transaction, before it writes, resolve checks that nothing the decision depends on has changed. The memory under the new memory's key, and every candidate the decision supersedes, deletes or confirms, or names as superseding the new memory, must still have the version and updated_at that find_conflicts read. A memory written since counts as changed, also when a 0.5.x store wrote it, which sets updated_at without bumping the version. So does one deleted or expired since, and a live memory under the new key where find_conflicts found none. resolve then raises ConflictsChanged with those keys, writes nothing and does not retry: run find_conflicts again and decide again. Candidates the decision keeps are not checked, and confirming a memory changes neither its version nor updated_at, so a confirmation in between never counts.

    The write id comes from find_conflicts. If a resolve of the same Conflicts already committed, as when an error left its outcome unknown and the caller calls again, resolve writes nothing and returns that write's result rebuilt from its rows, with already_applied set, whatever decision this call passes. As with reconcile, a rebuilt result lists only what the rows prove: kept is empty, and on a store without history so are superseded and deleted. Such a store keeps no row of a decision that only supersedes or deletes. When the commit of such a resolve is lost, its retry finds those memories gone, as the decision asked. So once an attempt of the call may have committed (it sent its COMMIT and failed with an error other than a serialization failure or a deadlock, which roll the attempt back), a memory the decision supersedes or deletes, the one under the new key included, counts as unchanged when it is gone. The retry applies the decision again, which changes nothing there, and returns its result without already_applied, since no row proves the earlier commit. After only serialization failures or deadlocks (40001, 40P01), which roll attempts back, the retry checks as strictly as the first attempt: a memory gone since was removed by another writer, and is a change. Once an attempt may have committed, the retries after it stay lenient, whatever error ends them next. A new call checks strictly again too: if an error escaped an earlier call, as when its retries ran out or the hang guard stopped it, and the caller calls resolve again, such a decision raises ConflictsChanged naming the keys that the earlier call removed. find_conflicts then shows the current state.

    Without a valid_at given to find_conflicts, the new memory stores no valid time, so it is valid from its write, and the versions the decision ends end at that write. A Conflicts and a Decision can wait in a LangGraph checkpoint while a person decides: resolve takes them as the checkpoint gives them back.

    setup() ¶

    Create the store's tables and run its migrations.

    MUST be called the first time the store is used. Safe to run from several processes at once: every migration is idempotent and versions are recorded with ON CONFLICT DO NOTHING. A setup() that finds another process still applying migration 2 waits for it, for up to SCHEMA_CHANGE_SETTLE_SECONDS, before it records the migration, so no store writes the new columns before they exist. When no job applies the migration, as after a peer's migration failed, it applies the migration itself. With an index, it creates the vectors table and its C-SPANN index (unless flat) on every call, then checks an existing index against the configuration. With history, it creates the history table, and with ttl_days turns on CockroachDB row-level TTL there. With a TTL configuration, it then turns on CockroachDB row-level TTL on expires_at.

    It reads a table's TTL settings first and changes them only when they differ from the configuration. On CockroachDB v25.4 a TTL change fails while another schema change runs on the same table, such as a vector index that another setup() builds. That error is retried with the budget that schema_change_policy gives it, up to ten minutes by default for each table, even if the policy's retry_on would refuse it; max_attempts=1 turns this off.

    An application role that did not run setup() needs SELECT, INSERT, UPDATE and DELETE on the store's items and vectors tables, and on the history table when history is on. With history off, it still needs SELECT and DELETE on a history table that exists, left from when history was on, for delete_namespace. Without SELECT on the migrations table, or without a migrations table, as when the tables were created without setup(), the store finds migration 2 through the items table's columns instead. On a multi-node cluster, one write can then fail in the seconds after setup() applies migration 2. Running setup() before rolling out 0.6.0, or granting SELECT on the migrations table, avoids that. The first store call inside a transaction the caller opened gets the permission error once. Only the SELECT grant avoids it.

    AsyncCockroachDBStore¶

    Asynchronous store.

    langchain_cockroachdb.store.aio.AsyncCockroachDBStore ¶

    Bases: AsyncBatchedBaseStore, BaseCockroachDBStore, AsyncPsycopgOps

    Async LangGraph store that keeps long-term memory in CockroachDB.

    The async twin of CockroachDBStore: same tables, same SQL, same behavior. For production, pass a psycopg_pool.AsyncConnectionPool or use from_conn_string with pool_config: a pool replaces broken connections, while a single connection cannot recover from a dropped one.

    aget, aput, asearch and the other awaited calls, and the sync wrappers, go through AsyncBatchedBaseStore's queue, which runs one abatch at a time. So a pool does not run those calls in parallel, and a large pool does not speed them up. What the queue gives instead is coalescing: ops queued in the same tick run as one batch, with one round trip per read group and one transaction for the writes. Only direct abatch calls, or sync batch calls from other threads, run concurrently on a pool.

    The constructor must run inside a running event loop, because AsyncBatchedBaseStore starts a task on it there. Awaited calls made in the same tick (aget, aput, asearch and the others) are coalesced into one abatch. The sync methods (get, put and the others) are meant for other threads while that loop runs. They run the async methods on it, so get, put, search, delete and list_namespaces join the same queue, while batch runs abatch directly. From the loop itself they raise asyncio.InvalidStateError. When the loop is closed or not running, or the call comes from a forked child of the process that created the store, they raise RuntimeError instead of waiting forever, as AsyncCockroachDBSaver's sync methods do.

    A batch runs its reads first, then all its puts and deletes in one transaction. Its gets, its searches and its listings take one round trip each. On a store with a vector index, semantic searches under a namespace add one before the searches, to find their namespaces, and one after them when a search must run again exactly. A flat store adds neither. The long-term memory guide explains why.

    With history, a batch that overwrites or deletes a memory first copies the version it ends into a history table, in its transaction. adelete then keeps the memory in history; apurge removes a memory with its history, and ahistory lists the old versions.

    afind_conflicts, aresolve, areconcile, aconfirm, arecord, aput_if and adelete_if are CockroachDBStore's methods of the same names without the prefix, as coroutines. They run on the caller's event loop, not through the queue, so on a pool they run concurrently. A reconcile policy and a confirm TTL function are plain functions that run on the event loop inside the transaction.

    Write a memory and settle the memories it may conflict with, in one transaction.

    The async form of CockroachDBStore.reconcile, which describes the decisions and the result in full. The candidates are the ones afind_conflicts finds. They are read in the transaction, policy decides what to do with the new memory and with each candidate, and the decision is applied before the transaction commits. Serializable isolation covers all of it: if another writer changes what the policy saw, one of the two transactions retries, and its policy sees the other's write. Two agents that reconcile contradicting memories for one user cannot both win.

    policy is a plain function, not an async one, which is refused before any I/O. It runs on the event loop, inside the transaction, and runs again on every retry, so it must be fast and deterministic: the loop runs nothing else while it runs. An LLM judge, or a person, belongs in afind_conflicts and aresolve, which hold no transaction while the decision is made. A policy must not call the store either: the store holds its connection while the policy runs, so such a call raises RuntimeError at once. A policy that raises rolls the transaction back, and its exception propagates unchanged, without a retry. So does the ValueError for an invalid decision.

If an attempt commits and its result is lost, as when the connection drops while the COMMIT's answer travels, the retry finds the rows that carry its write id and writes nothing.     aresolve(conflicts, decision) async ¶

    Apply a decision about what afind_conflicts found, in one transaction.

    The async form of CockroachDBStore.resolve, which describes the checks and the retries in full. This is the second step of the two-step flow: afind_conflicts reads the candidates, an LLM or a person decides while no transaction is open, and aresolve applies the decision as areconcile applies a policy's. It writes the new memory that afind_conflicts planned, with its provenance, valid time and write id, and the vectors it embedded then, so nothing is embedded again.     In the same transaction, before it writes, aresolve checks that the memory under the new memory's key, and every candidate the decision supersedes, deletes or confirms, or names as superseding the new memory, still has the version and updated_at that afind_conflicts read. If one changed, it raises ConflictsChanged with those keys, writes nothing and does not retry: find the conflicts again and decide again. Candidates the decision keeps are not checked, and a confirmation in between never counts.

Once an attempt of the call may have committed (it sent its COMMIT and failed with an error other than a serialization failure or a deadlock), a memory the decision supersedes or deletes counts as unchanged when it is gone, for the rest of the call.     setup() async ¶

    Create the store's tables and run its migrations.

    MUST be called the first time the store is used. Safe to run from several processes at once: every migration is idempotent and versions are recorded with ON CONFLICT DO NOTHING. A setup() that finds another process still applying migration 2 waits for it, for up to SCHEMA_CHANGE_SETTLE_SECONDS, before it records the migration, so no store writes the new columns before they exist. When no job applies the migration, as after a peer's migration failed, it applies the migration itself. With an index, it creates the vectors table and its C-SPANN index (unless flat) on every call, then checks an existing index against the configuration. With history, it creates the history table, and with ttl_days turns on CockroachDB row-level TTL there. With a TTL configuration, it then turns on CockroachDB row-level TTL on expires_at.

    It reads a table's TTL settings first and changes them only when they differ from the configuration. On CockroachDB v25.4 a TTL change fails while another schema change runs on the same table, such as a vector index that another setup() builds. That error is retried with the budget that schema_change_policy gives it, up to ten minutes by default for each table, even if the policy's retry_on would refuse it; max_attempts=1 turns this off.

    An application role that did not run setup() needs SELECT, INSERT, UPDATE and DELETE on the store's items and vectors tables, and on the history table when history is on. With history off, it still needs SELECT and DELETE on a history table that exists, left from when history was on, for delete_namespace. Without SELECT on the migrations table, or without a migrations table, as when the tables were created without setup(), the store finds migration 2 through the items table's columns instead. On a multi-node cluster, one write can then fail in the seconds after setup() applies migration 2. Running setup() before rolling out 0.6.0, or granting SELECT on the migrations table, avoids that. The first store call inside a transaction the caller opened gets the permission error once. Only the SELECT grant avoids it.

    Policies¶

    A policy is a function of the Proposal and the sequence of candidates that returns a Decision, typed as Policy (Callable[[Proposal, Sequence[Candidate]], Decision]). It runs inside the reconcile's transaction, and again on every retry, so it must be a plain function, fast and deterministic, and must not call the store. These are the built-in ones, and validate_decision, which checks a decision as reconcile and resolve do.

    langchain_cockroachdb.store.reconcile.supersede_same_slot() ¶

    Return a policy that supersedes older facts in the same slot.

    1. If the memory under the proposal's key (the target) has a later valid_at, skip the proposal, whatever reason the target has.
    2. Otherwise, if no candidate is in the same slot (reason "slot"), write the proposal and keep every candidate.
    3. If a slot candidate has a later valid_at, record the proposal as superseded by the latest such candidate.
    4. Otherwise, supersede all slot candidates.

    langchain_cockroachdb.store.reconcile.skip_duplicates(threshold=0.97) ¶

    Return a policy that skips a memory that repeats one already stored.

    A new memory, one with no live memory under its key, is skipped when a candidate has an equal value or scores at or above threshold, and the highest-scoring such candidate is confirmed (an equal value counts as score 1.0). When the proposal has a slot, only candidates in the same slot count: a repeat outside the slot states another fact, and skipping the new memory for it would leave an older memory in the slot live, which may contradict the new one. A memory whose key holds a live memory is skipped only when it saves that memory's value again, which confirms it. Any other value there is an update, which this policy never skips, whatever repeats it under another key: skipping it would leave the key with its old value, which may contradict the new one. Then it returns the decision that writes the new memory and keeps every candidate, so first_of moves on to the next policy.
